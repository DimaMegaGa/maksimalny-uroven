# Контракт сайта и сервера

Сайт отправляет относительные запросы `/api/...` на свой домен. Код клиента: `frontend/app.js`, функции `api`, `acceptState`, `mutate`, `refreshFromServer`. GET не имеет тела; POST использует JSON и заголовок `X-Maks-Request: 1`. Cookie передаются автоматически. Не хранить пароль или токен в localStorage.

## 1. POST /api/login

Тело: `{role, name, school, className, code}`. role: `student` или `teacher`. className обязателен только ученику. code — введённый пользователем секрет. Форма сейчас проверяет минимум 6 символов; правила приглашения учителя и создания ученика реализует сервер.

Нужно найти профиль по устойчивому ключу (в текущей форме: нормализованные роль + имя + школа), проверить хеш кода, сверить класс. Создание нового профиля допустимо только по выбранным правилам регистрации/приглашения. Не считать неизвестный профиль успешным входом автоматически. Для однофамильцев с одинаковым полным именем стоит добавить отдельный логин или школьный ID в форму.

Успех: HTTP 200, snapshot ниже и Set-Cookie `maks_session=...; HttpOnly; SameSite=Strict; Path=/`. В HTTPS добавить Secure. Токен генерировать случайно, в базе хранить его хеш и срок действия.

Ошибка: HTTP 400/401/403/429 и `{ "error": "Понятное сообщение" }`. Ограничить попытки входа и добавить восстановление кода.

## 2. GET /api/state

Проверить сеанс. Без сеанса — HTTP 401 с JSON error. Успех — HTTP 200:

```json
{
  "userId": "идентификатор вошедшего пользователя",
  "revision": 0,
  "db": {
    "users": [],
    "tasks": [],
    "submissions": [],
    "notifications": [],
    "exchanges": [],
    "ledger": []
  }
}
```

В users обязательно должен находиться вошедший пользователь. Остальные массивы могут быть пустыми. Не отдавать хеши кодов, сеансы и внутренние настройки. Сайт опрашивает этот маршрут каждые 3 секунды и перерисовывается при изменении revision. Открытые формы и модальные окна при опросе не перерисовываются.

### Поля записей (camelCase)

SQL-названия из schema.sql преобразовать в эти названия. JSON-строки photos_json/achievements_json распаковать в массивы.

- users: `id, role, name, school, className, avatar, achievements, createdAt`.
- tasks: `id, teacherId, school, title, description, instructions, subject, points, deadline, targetType, target, createdAt`.
- submissions: `id, taskId, userId, review, photos, status, createdAt, checkedAt`.
- exchanges: `id, userId, teacherId, subject, cost, status, createdAt`.
- ledger: `id, eventId, userId, amount, text, createdAt`.
- notifications: `id, userId, type, title, text, target, eventId, createdAt, read, celebrated`. Для повышения уровня дополнительно: `levelTitle, levelThreshold, submissionId`.
- achievements внутри пользователя: `id, kind, threshold, title, description, icon, earnedAt`.

id — строка. createdAt, checkedAt, earnedAt — Unix-время в МИЛЛИСЕКУНДАХ. deadline — строка `YYYY-MM-DD`. read/celebrated — JSON boolean. Отсутствующую аватарку отдавать как пустую строку. photos/achievements всегда массивы. instructions — строки шагов через перенос строки.

Статусы submission: pending / approved / rejected. Статусы exchange: pending / approved / rejected. targetType: student / class / parallel. target — ID ученика либо строка класса/параллели.

В текущем интерфейсе фото — JPEG data URL, сжатый браузером; при переходе на файловые URL нужно адаптировать imageData(), загрузку и проверки avatar(). Максимум три фото ответа. На сервере проверить размер и содержимое файлов; не доверять одному MIME-типу.

### Фильтрация

users — публичные профили, разрешённые политикой платформы. tasks — ученику только назначения его школы и класса/параллели/ID; учителю — его задания. submissions — ученику только свои, учителю только на его задания. exchanges — только участникам запроса. notifications — только адресату.

ledger необходим клиенту для публичных сумм опыта, но полную историю чужих операций раскрывать нежелательно. Для первого пилота можно ограничить выдачу общей школьной областью. Для рабочего запуска добавьте отдельные публичные агрегаты earnedTotal/completedTotal и адаптируйте experience(), balance(), profile(), ranking(), чтобы не отдавать чужой журнал целиком. Никогда не отдавайте постороннему пользователю отзывы и фотографии чужих работ.

## 3. POST /api/commit

Тело: `{ "revision": 12, "changes": { "tasks": [], "submissions": [], "users": [], "notifications": [], "exchanges": [], "ledger": [] } }`.

mutate() получает состояние, выполняет интерфейсное действие и присылает только новые/изменённые записи. Это транспорт заготовки, НЕ разрешение произвольной записи в таблицы. Сервер должен распознать допустимое действие, проверить его и вычислить последствия самостоятельно. Удаления через этот контракт не предусмотрены.

В одной транзакции:

1. Проверить сеанс и роль.
2. Проверить revision. Устаревший — HTTP 409, изменения не применять. Клиент перечитает данные и предложит повторить действие.
3. Проверить каждую запись по правилам ниже.
4. Зафиксировать записи, награды, уведомления и новую revision атомарно.
5. Вернуть новый snapshot.

### Обязательные правила

- users: можно менять только собственную аватарку; роль, школа, имя, чужие профили и achievements через обычный commit не редактируются.
- tasks: только учитель. teacherId и school брать из сеанса. Баллы — целое 1–100. Проверить предмет по каталогу и срок. Индивидуальный адресат должен быть учеником той же школы.
- submissions: ученик отправляет только своё доступное задание; сервер задаёт userId/status. Одна работа на пару taskId+userId. Повторная отправка допустима только после rejected. Нельзя заменить taskId существующей работы.
- Проверка: только создатель задания меняет pending на approved/rejected. Не принимать чужой статус из формы ученика.
- ledger из changes НЕ сохранять. При approved сервер добавляет одну запись с eventId `approved:ID_РАБОТЫ`. UNIQUE(event_id) защищает от двойной награды. Повторная проверка уже обработанной работы не меняет баланс.
- exchanges: ученик создаёт запрос по каталогу, teacherId проверяется по школе; стоимость берётся с сервера. Один pending-запрос на предмет и ученика. При одобрении учителем проверить баланс в транзакции, списать один раз с eventId `exchange:ID_ЗАПРОСА`.
- notifications: клиент может только отметить свои read/celebrated. Новые уведомления создаёт сервер по факту действия. Не сохранять произвольные сообщения из changes.

Не доверять даже тем проверкам, которые уже есть в app.js: браузерный код можно изменить.

### Награды и уведомления

Опыт = сумма положительных начислений; баланс = сумма всех операций. Обмен не снижает уровень. Пороги: 60 — «Активный», 120 — «Лидер».

После перехода уровня сохранить achievement и уведомление type=level с levelTitle, levelThreshold, submissionId; eventId `level:ID_УЧЕНИКА:ID_ДОСТИЖЕНИЯ`. Повторное начисление того же достижения запрещено. victory-окно уже реализовано на клиенте.

После подтверждения создаётся reward-уведомление с тем же eventId, что и запись награды в ledger. При публикации — type=task, eventId `task:ID_ЗАДАНИЯ`. При отправке работы — review учителю. При возврате — revision ученику. Если баланс впервые пересёк стоимость предмета — exchange ученику. Поле target — маршрут интерфейса: tasks, exchange, profile или home.

Каталог и стоимость предметов находятся в SUBJECTS в app.js. Сервер должен иметь собственную копию каталога (Математика 30, История 25, остальные 20) или хранить его в БД и отдавать отдельным API после адаптации интерфейса.

## 4. POST /api/logout

Тело `{}`. Отозвать серверный сеанс и очистить cookie. Ответ HTTP 200 `{}`. Профиль не удалять.

## Замена архитектуры

Если друг предпочитает отдельные маршруты `/tasks`, `/submissions`, `/approvals`, это допустимо и удобнее для большого проекта. Тогда необходимо заменить mutate() и места его вызова в app.js. Остальные компоненты можно сохранить. Для первого подключения проще реализовать четыре текущих маршрута, сохранив строгую серверную проверку действий.
